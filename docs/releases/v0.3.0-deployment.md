## 전환 순서

1. 운영 중인 상태로 Run 73개의 key 정렬 export SHA-256과 artifact 목록을 기록했다(실행 중 Run 0개).
2. 직전 배포를 백업 도구로 백업하고 검증했다. 그 뒤 새 Run이 없음을 확인하고
   백업 예약 → 서비스 정지 → 서비스 제거 순으로 내렸다. 직전 배포·이미지·백업은 보존했다.
3. 새 배포의 인수용 저장소를 `staging-store/`로 옮기고, 백업의 store 파일 688개를 복사해
   크기·SHA-256을 대조했다(불일치 0, `migration.json`).
4. API 포트를 18088로 바꾸고 서비스를 설치했다. 첫 시작에서 schema v3→v4 이행이
   `store/backups/schema-v3-before-v4-*.zip`을 먼저 만든 뒤 진행됐다.
5. 이행 후 73개 Run의 export·artifact가 1단계 기록과 모두 같았다.

되돌릴 때는 새 운영 기록을 먼저 백업한다. 그다음 [상시 실행](../local-service.md)과
[백업/복원](../local-backup.md)의 소유권 검사를 따라 직전 배포를 다시 등록한다.
**v4로 이행한 store는 직전 controller가 열 수 없다.** 직전 배포로 돌아가려면 그 배포의 store를
그대로 쓰거나 이행 전 백업(위 2단계 백업 또는 `schema-v3-before-v4-*.zip`)을 복원한다.
이 경우 전환 후 생성한 Run은 보이지 않는다.

전체 Career 13+4 실행은 별도 인수용 저장소(`staging-store/`, `staging-acceptance/`)에서 수행했다.
운영에서 다시 실행하지 않았으며, 별도 실행을 운영 이력과 합치지 않았다.

처음 별도 배포 브라우저 전체 실행에서 3건이 실패했다. 이 3건은 기존 화면 서버 주소가 필요한데,
외부 서버 모드의 기본값(`127.0.0.1:18080`)에는 서버가 없었다. 별도 배포 API 주소와 전환 동작을
지정해 다시 실행했고 통과했다. 40건 생략은 Docker·Career 환경 변수가 필요한 테스트이며,
해당 범위는 실제 Career 브라우저 실행과 저장 증거 테스트로 따로 확인했다.
Java CLI는 오프라인 catalog로 정의를 먼저 검증하므로 Career 시나리오를 거절한다.
그래서 Equity smoke는 API에 직접 제출했다.

## 증거와 한계

로컬 기록은 `.lab/verification/v0.3.0/`에 있다: 빌드·인수·브라우저 로그,
`before-cutover-history.json`/`after-cutover-history.json`/`restore-history.json`(Run별 정렬 export hash),
`final-prod-backup.log`, smoke 결과, `final-audit.json`. 배포 경로에는 `migration.json`,
`staging-acceptance/`, 이관한 직전 인수 기록 `acceptance/`가 있다.
검증용 프로세스는 종료했고 저장소·백업·배포 이미지·증거는 보존했다.

재시작 검증은 정상 종료·재개방과 백업에 의한 재기동이다. privileged Docker daemon 장애,
실제 로그아웃·호스트 재부팅, 외부 공개 환경은 다시 시험하지 않았다.
기존 [운영 제한](v0.1.0.md#운영-제한)과 [실패 주입 검증 범위](../worker-fault-injection.md)를 유지한다.
