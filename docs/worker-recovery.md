# Worker 비정상 종료 후 접수와 복구

등록된 LOCAL_JVM 실행기는 worker 시작 전에 관리자 소유 workspace에 복구 기록을 만든다.
sequence의 기본 경로는 `.lab/worker-workspaces/.active-sequence-worker.properties`다.
저장소 경로를 변경했다면 해당 저장소의 `worker-workspaces`를 확인한다.
정상 실행 중에도 기록이 존재하며, 기록 자체가 장애 발생을 뜻하지는 않는다.

## 자동으로 보장하는 범위

기록은 Run ID, 배포 SHA-256, 시작 시각과 임의 소유권 token을 포함하며 최대 4 KiB다.
배타 생성 후 파일 쓰기를 force한 다음 worker를 시작한다. 기존 기록, 불완전한 파일,
심볼릭 링크 또는 접근 여부를 확인할 수 없는 경로는 접수를 차단한다.
실행기당 파일 하나를 사용하며 Run 수에 비례하는 메모리나 복구 목록을 만들지 않는다.

worker 성공 결과와 프로세스 종료·입출력 정리·메트릭 drain을 확인한 경우에만 자신이
작성한 기록과 일치하는 파일을 제거한다. 제거 실패도 Run 실패로 처리한다.
실패, 인터럽트, 정리 미확인, controller 강제 종료는 기록을 남긴다.
자원 정리가 끝난 일반 실험 실패도 보수적으로 운영자 확인을 요구한다.
중앙 Run 증거 완료 처리는 이 절차 이후 기존 runner가 담당한다.

같은 저장소와 실행기 ID로 재시작하면 기록이 다시 적용된다. readiness는 캐시된 Docker
probe보다 먼저 `INCOMPATIBLE` / `WORKER_ACTIVE_OR_RECOVERY_REQUIRED`를 반환한다.
기록이 있는 시점의 새 접수는 HTTP 503이며 새 Run을 만들지 않는다.
동시에 사전 검사를 통과한 접수도 파일 배타 생성으로 보호하며, 이 경쟁에서 패한
접수는 이미 생성된 Run을 `WORKER_RECOVERY_REQUIRED`로 실패 처리할 수 있다.
기존 Run·CHECK·보고서는 계속 조회할 수 있다.

## 운영자 복구 절차

1. 기록의 Run ID로 Run 상태와 증거를 조회한다. 정상 실행 중이면 완료를 기다린다.
2. 복구가 필요하면 controller를 정지한다. 이전 worker와 자손 프로세스가 종료됐는지
   실제 실행 파일·명령·작업 경로를 대조한다. PID만으로 종료 대상을 판단하지 않는다.
3. Docker가 응답하는 상태에서 해당 Run의 컨테이너를 조사한다. sequence는
   `engineering-lab.run-id=<Run ID>` 라벨을 사용한다. 라벨은 조사 단서이며 단독 소유권
   증명이 아니다. 생성 정보와 Testcontainers 세션을 대조하여 해당 실행 소유 자원만
   정리한다. 다른 세션의 컨테이너나 공유 Docker 전체를 정리하지 않는다.
4. 해당 실행의 프로세스·컨테이너 정리를 확인한 후 복구 기록과 조사 결과를 별도 보관하고,
   **해당 `.active-<실행기 ID>.properties` 파일 하나만** workspace 밖으로 이동한다.
   controller가 실행 중일 때 파일을 변경하지 않는다.
5. 동일 저장소·실행기 ID로 controller를 시작하고 readiness가 READY인지 확인한다.
   작은 시나리오 한 번으로 성공·증거 저장·복구 기록 제거를 확인한다.

Docker에 접근할 수 없거나 소유 자원 정리를 확인하지 못했다면 기록을 해제하지 않는다.
불완전한 기록은 이전 Run 이력·로그·작업 폴더로 조사하며, 기록 해독 실패만을 이유로
삭제하지 않는다. HTTP 강제 해제 API나 자동 재시도·자동 컨테이너 삭제는 제공하지 않는다.

## 제한과 후속 작업

이 기능은 미확인 자원이 남은 상태에서 새 worker를 추가 실행하지 않도록 하는 보호 장치다.
컨테이너 자동 회수와 Docker daemon/호스트 장애 후 자동 조정은 아직 구현하지 않았다.
자손 프로세스는 아래의 관찰 기반 종료 범위만 지원한다. 프로세스 강제 종료 후 기록 보존을 테스트했지만 디렉터리 fsync를
포함한 전원 장애 내구성을 보장하지 않는다. workspace는 관리자만 수정할 수 있어야 한다.
저장소 경로나 실행기 ID를 변경하면 이전 기록이 적용되지 않으므로 배포 시 유지한다.
이 기능 도입 이전의 실행과 readiness probe 자원은 기록 대상이 아니므로 별도 조사한다.

후속 단위는 소유 자원 기록과 제한된 재조정, daemon 장애 실험, OS 수준 프로세스 격리다.
전체 D4 장애 복구 완료와 이 접수 보호 단위의 완료를 구분한다.

## 실행 중 관찰한 자손 프로세스 종료

`WorkerProcess`는 50ms 간격으로 직접 worker의 자손을 관찰하고 실행 전체에서 최대
128개의 ProcessHandle·시작 시각을 보관한다. 매 관찰에서도 최대 128개까지만 탐색한다.
종료 시 관찰 스레드를 멈추고 자손과 worker에 종료 신호를 보낸다. 종료 유예 뒤에도
살아 있으면 강제 종료하며, 두 단계 모두 기존 `Limits.stopGrace`를 적용한다.
기본 유예는 단계별 30초다. 관찰 스레드 종료 대기에도 같은 상한을 적용한다.
신호 전 시작 시각을 대조하며 PID가 재사용된 다른 프로세스에는 신호를 보내지 않는다.

관찰 수 초과, 살아 있는 프로세스의 시작 시각 조회 실패, 탐색/종료 권한 오류 또는
종료 미확인은 `PROCESS_TREE_CLEANUP_UNCONFIRMED`로 실패한다. 정상 RESULT가 있어도
성공을 반환하지 않으며 등록 worker의 복구 기록은 유지된다. 호출 스레드 인터럽트도
정리 단계를 생략하지 않고 정리 이후 인터럽트 상태를 복원한다.

이 기능은 controller가 살아 있는 동안 **관찰된 자손**을 정리한다. 50ms 사이에 생성된 뒤
관계가 끊긴 프로세스, 이미 분리된 자손이 새로 만든 프로세스, controller 강제 종료 후
고아 프로세스까지 탐지·회수하는 격리 기능은 아니다. Docker 컨테이너도 대상이 아니다.
이 범위 밖 자원은 위 운영자 복구 절차로 확인해야 한다. OS의 프로세스 조회·신호 호출
자체를 강제 중단하는 시간 보장은 없으며, 악의적인 worker를 격리하는 sandbox도 아니다.
