## 실행 구성과 데이터 보존

- 대시보드: <http://127.0.0.1:4188/app/experiments>
- API: <http://127.0.0.1:18088/dashboard/v1/modules>
- 운영 경로: `.lab/deployments/v0.1.0-20261016` (준비 날짜를 경로에 유지).
- Java 25 controller, Java 21 worker 6종, Node 24.19.0 frontend를 고정했다.
  `deployment.json`에는 이미지 ID, jar hash, 태그와 frontend hash를 포함한
  `release` 메타데이터를 기록했다. 이 파일은 정기 백업에도 포함된다.
- Run의 Git 출처는 `.lab/release-provenance/v0.1.0` detached checkout으로 고정한다.
  이 경로를 삭제하면 새 실행의 Git 출처 조회가 실패하므로 배포와 함께 보존한다.
- 두 LaunchAgent는 새 배포의 runner와 절대 경로를 사용한다. 이전 서비스와 백업
  예약의 소유권을 확인한 뒤 제거했으며 이전 배포 파일·이미지·백업은 보존했다.
- 예약 백업은 새 배포를 대상으로 매일 03:00 KST에 실행하고 최근 7개를 보존한다.
  저장 경로는 `.lab/backups/v0.1.0-20261016`이다. 예약과 같은 LaunchAgent를
  즉시 실행해 백업 검증·서비스 재개와 종료 코드 0을 확인했다.

별도 API 18089/frontend 4189와 독립 저장소에서 먼저 검증했다. 이후 이전 서비스를
정상 정지하고 POSIX 저장소 잠금 아래 최신 백업을 만들었다. 백업 manifest와
복사한 모든 store 파일의 크기·SHA-256을 대조한 뒤 새 운영 서비스를 시작했다.
기존 Run 27개의 metadata가 전환 전후 동일했으며, 이전 인수 실행 17개의 CHECK,
REPORT 다운로드와 canonical NDJSON export hash도 재검증했다.

별도 검증 저장소는 `staging-store/`, 결과는 `staging-acceptance/`에 분리 보존한다.
이 저장소의 검증 실행을 운영 이력과 병합하지 않았다. `migration.json`, `cutover.json`,
`before-upgrade-runs.json`에 백업 경로·파일 해시·이관 비교 결과가 있다.

## 메모리 부족 원인과 재검증

최초 Career 검증에서는 Docker 메모리 부족으로 테스트 MySQL이 종료됐다
(`OOMKilled=true`, exit 137). 첫 실패와 동일 조건의 재시도 로그를 보존했다.
사용자 승인 후 약 5 GiB를 사용하던 `code-drill-rabbitmq-1`만 일시 정지하고
테스트를 다시 실행해 전체 150개가 통과했다. 테스트 조건·데이터 크기를 줄이거나
테스트를 비활성화하지 않았다. 공유 Docker 엔진을 재시작하거나 prune하지 않았다.
검증 후 일시 정지했던 동일 ID의 RabbitMQ 컨테이너를 재시작했으며,
`running`과 Docker healthcheck `healthy`를 확인했다. 재시작 이후에도 운영 모듈
전체 READY와 데이터·배포 파일 해시를 다시 확인했다.

## 증거와 운영 주의

실행 로그와 브라우저 캡처는 `.lab/verification/v0.1.0-upgrade/`, 고정 배포와
인수 결과는 `.lab/deployments/v0.1.0-20261016/`에 있다. 로컬 Run ID와 이미지 ID를
다른 PC에서 그대로 사용할 설정으로 Git에 복사하지 않는다.
운영 결과는 `acceptance/index.json`과 `acceptance/reopen.json`, 이전 증거는
`previous-acceptance/`, 최종 모듈·해시·자원·RabbitMQ 상태는 `final-audit.json`,
최근 백업 경로는 `backup-last-success.json`에 기록했다.

이전 배포의 store는 전환 시점 사본이다. 되돌릴 때는 먼저 새 운영 배포를 백업하고
중지한 뒤 호환성 및 이관 대상을 확인해야 한다. 이전 store로 단순 전환하면 새 배포에서
추가된 실행이 보이지 않는다. [상시 실행](../local-service.md)과
[백업·복원](../local-backup.md)의 소유권 검사·새 경로 복원 절차를 따른다.

인수 범위는 단일 호스트의 loopback 운영이다. 실제 로그아웃·호스트 재부팅·외부 공개
환경을 새로 검증한 결과는 아니며, [릴리스 제한](v0.1.0.md#운영-제한)은 유지한다.
